# Анализ ручных действий бота

Журнал `manual_actions` хранится в той же SQLite, что и анонсы. Он включён в production DI без дополнительной настройки. Таблица и индексы создаются при старте; существующие анонсы и журналы не изменяются.

Записывается каждое полученное `Message` и `CallbackQuery`: команды с аргументами, пошаговый ввод, массовый ввод анонсов, редактирование, модерация, подтверждение и пропуск черновика, отмена, footer, принудительная публикация, неизвестный ввод и сообщения неподдерживаемого типа. Содержимое файлов не скачивается. Текст и caption сохраняются; у запрещённых действий сохраняются только метаданные. Частный пользовательский ввод тоже попадает в журнал, поскольку бот принимает заявки на модерацию.

В записи есть время UTC, Telegram update/message/callback id, пользователь и чат, вид действия, нормализованное имя команды/кнопки или шаг ввода, текст, имя обработчика, связанная сущность/ссылка, шаг до и после и снимки значений JSON. Аргументы отделены от имени действия для группировки статистики. Числовой суффикс callback сохраняется в `entity_id` и исходном `input_text`.

Связи: `review_draft` использует RSS post id; `announcement` — id анонса; `pending_announcement` — id заявки; `footer` — id footer. При наличии RSS-связи используются также `source_link` и `announcement_parse_attempts`. Если сущность ещё не создана, записи связываются по пользователю, времени, шагам и введённой ссылке. Массовый ввод — одна запись на сообщение; все блоки остаются в `input_text`, а не преобразуются в выдуманную единственную сущность.

Снимки фиксируют значения до изменения и после, включая данные перед удалением. Для отдельных правок уже существуют дополнительные таблицы `announcement_edits` и `announcement_review_edits` с историей каждого изменённого поля. Журнал обновлений дополняет их вводом, кнопками и действиями без изменения данных.

## Статусы

- `received`: запись сохранена перед обработкой, завершение пока не записано. Долгое нахождение в этом статусе требует проверки: возможны остановка процесса или ошибка финальной записи аудита.
- `handled`: обработчик завершился без исключения. Это **не гарантия изменения БД**: сюда относятся подсказки, сообщения о невалидном аргументе, уже обработанные кнопки и команды просмотра. Для эффекта смотрите снимки и таблицы изменений полей.
- `awaiting_input`: обработчик ввода завершился, но диалог остался на том же шаге. Это помогает найти повторный ручной ввод, но само по себе не доказывает ошибку валидации.
- `ignored`: подходящий обработчик не найден либо тип сообщения не обрабатывается.
- `denied`: забаненный пользователь, callback вне админ-чата или административная команда вне админ-чата. Текст и снимки не сохраняются.
- `error` / `cancelled`: обработчик выбросил исключение / исключение отмены. Сохраняется только тип исключения; исходное исключение продолжает обычный путь обработки.

Если начальная запись аудита не удалась, действие не начинается. Аудит обновления не объединён одной транзакцией с Telegram-запросами и всеми бизнес-изменениями: при сбое после побочного эффекта запись может остаться `received` или `error`. Повторные доставки Telegram не подавляются аудитом: они записываются отдельно и различаются по `id`, сравнивать их можно по `update_id`.

## Быстрый отчёт

Скрипт использует стандартную библиотеку Python 3, открывает SQLite в режиме `mode=ro` и печатает JSON. Запускайте с правами чтения рабочей БД и её WAL-файлов либо на согласованной SQLite backup-копии.

```bash
python3 scripts/manual-actions-report.py --db /opt/WeekChgkSPB/data/posts.db
python3 scripts/manual-actions-report.py --db /opt/WeekChgkSPB/data/posts.db --since 2026-10-16
python3 scripts/manual-actions-report.py --db /opt/WeekChgkSPB/data/posts.db --post-id 3418779 --details
```

По умолчанию отчёт охватывает последние 7 дней и последние 50 действий. `--limit` меняет количество подробных записей; статистика считается по всему выбранному периоду. `--details` включает снимки до/после. Дата без TZ трактуется как UTC.

Отчёт показывает частые действия и повторяющиеся шаги, число ошибок и незавершённых действий, причины автоматического отказа для связанных постов и последние примеры ввода. `parser_reasons` использует текущее сохранённое состояние `announcement_parse_attempts`; причина на момент действия доступна в снимке черновика. История до внедрения аудита не восстанавливается.

Для отдельных полей:

```sql
SELECT field, COUNT(*) AS edits, COUNT(DISTINCT post_id) AS posts
FROM announcement_review_edits
WHERE edited_at_utc >= '2026-10-16'
GROUP BY field ORDER BY edits DESC;

SELECT field, COUNT(*) AS edits, COUNT(DISTINCT announcement_id) AS announcements
FROM announcement_edits
WHERE edited_at_utc >= '2026-10-16'
GROUP BY field ORDER BY edits DESC;
```

## Доступ и хранение

Текст ручного ввода нужен для воспроизведения проблем, поэтому журнал является частью рабочей БД и её резервных копий. Он не отправляется в Qwen и не печатается целиком в Docker-лог. Маскируются распространённые форматы Telegram/API-токенов, Bearer и пары `password/token/secret/api_key=...`, включая кавычки. Это не универсальное распознавание произвольных секретов; сообщения могут содержать персональные данные, введённые пользователем. Тексты исключений не сохраняются. Автоматического удаления истории нет.
